# Voiceover 当前功能与完整流程说明

> 基于当前工作区代码整理，更新时间：2026-08-14。本文以当前主用的局域网网页流程为准；仓库中仍保留 Tauri/桌面端兼容代码，但不是当前推荐入口。

## 1. 项目解决什么问题

Voiceover 将一本 EPUB、PDF 或 TXT 小说拆成章节，分析每句文字由谁说、应以什么情绪和节奏演绎，再生成角色一致的章节配音、背景音乐、音效和最终混音。

系统是“主机集中处理、浏览器操作”的局域网应用：书籍、数据库、模型配置、MiMo 密钥和音频文件都位于运行服务的主机，浏览器只负责操作与试听。当前没有登录、权限或书库隔离，因此只应部署在可信网络中。

## 2. 系统组成与职责

| 组成 | 默认端口/位置 | 职责 |
| --- | --- | --- |
| React 网页 | 开发时 `5173`；生产时由 `8000` 提供 | 书库、章节选择、分析/生成进度、审阅、试听、下载与重新生成 |
| Python 网页服务 | `8000` | HTTP API、上传、SQLite、文件流、任务队列、启动 Python Worker |
| Python Worker | 主机子进程 | 提取、分析、TTS、Whisper、Stable Audio、混音、MP3 转换 |
| SQLite | `AUDIOBOOK_DATA_DIR/audiobook.db` | 书籍、章节、角色、别名、批量任务和阶段耗时的持久化状态 |
| OpenAI 兼容 LLM | 由主机模型配置决定 | 角色、说话人、情绪/语速、动态演绎、场景、配乐和音效规划 |
| MiMo V2.5 | 云端 API | 固定音色参考、角色/旁白片段配音 |
| 本地 Whisper（MLX） | 主机 Python 环境 | 将原章节配音转成带时间戳的文本，供音频规划和混音定位使用 |
| 本地 Stable Audio 3（MLX） | `stable-audio-3/optimized/mlx/sa3` | 根据音频规划生成背景音乐和音效 WAV |
| ffmpeg | 主机 PATH | 音乐响度归一化、最终混音、MP3 转换、尖锐声检测的统计分析 |

## 3. 数据如何保存

默认数据目录由操作系统决定，也可通过 `AUDIOBOOK_DATA_DIR` 指定。每本书的核心结构如下：

```text
<data-dir>/
├── audiobook.db                         # 书库、章节、角色、批量队列
├── uploads/<uuid>-原始文件.epub          # 受应用管理的上传源文件
└── books/<book-id>/
    ├── chapters/chapter_001.txt          # 提取后的章节正文
    ├── scripts/chapter_001.json          # 可审阅、可生成的章节脚本（IR）
    ├── analysis/chapter_001/
    │   ├── state.json                    # 分析/生成阶段状态
    │   ├── characters.json … voice_direction.json
    │   ├── transcript.json               # Whisper 时间戳转录
    │   └── audio_plan*.json              # 场景、音乐、音效规划及阶段缓存
    ├── voice-profiles/                   # 每个稳定角色/旁白的 MiMo 参考 WAV 与元数据
    ├── segments/chapter_001/             # 每个 TTS 片段 WAV、缓存签名、timeline.json
    ├── audio/chapter_001.wav             # 原章节配音
    ├── audio/chapter_001_mixed.wav       # 最终混音
    ├── audio-assets/chapter_001/
    │   ├── music/*.wav
    │   ├── sfx/*.wav
    │   └── manifest.json
    └── exports/                          # MP3 和外部 API 的 ZIP
```

删除书籍时，服务会取消尚未完成的任务，删除该书的 SQLite 行、工作目录和由本应用管理且不再被其它书引用的上传缓存；不会删除用户桌面等外部位置的原始文件。

## 4. 从导入到最终音频的总流程

```text
上传 EPUB / PDF / TXT
        │
        ▼
提取正文 → 章节切分 → 章节预览与勾选
        │
        ▼
按书籍顺序分析所选章节（角色上下文逐章传递）
        │
        ├── 可选：人工审阅、合并别名、改性别/音色/旁白
        │
        ▼
自动或手动提交持久化批量队列
        │
        ├── 原章节配音（MiMo）
        ├── Whisper 时间戳转录
        ├── LLM 场景/背景音乐/音效规划
        ├── 本地 Stable Audio 生成资源
        └── ffmpeg 最终混音
        │
        ▼
网页试听、下载原配音/最终混音/单个音乐或音效；需要时转 MP3
```

分析阶段为了保证“下一章知道前面已有谁”而按章节顺序执行；生成阶段采用可恢复的章节级阶段调度：MiMo 配音全服务串行，而已完成配音章节的转录、规划、音频生成和混音可与下一章 MiMo 配音并行。

## 6. 阶段一：导入、提取与切章

### 输入与格式处理

- **EPUB**：用 `ebooklib` 读取正文文档，用 HTML 解析后合并文本，并尽量读取书名和语言元数据。
- **PDF**：先判断文字层。普通文字 PDF 用 PyMuPDF 提取；扫描件会走 OCR 回退；混合 PDF 会保留能提取的文字并给出 OCR 警告。
- **TXT**：优先按 UTF-8（含 BOM）读取，失败时回退到 GB18030。

提取器会规范换行、行内空白、部分 Gutenberg 式首字母/孤立引号，并去除部分版权/制作方括号信息。

### 章节切分

章节识别同时支持英文 `Chapter/Part/Book/Section` 和中文“第 X 章/节/卷/回/篇”。没有识别到标题时，会把全文作为 `chapter_001`，并降低切分置信度。每章正文独立保存，因此用户可以在分析前预览。

## 7. 阶段二：章节文本与角色分析

### 为什么拆成多个 LLM 调用

旧式“一次请求同时识别角色、分配台词、判断情绪、设计音色和规划音乐”的上下文过大，既容易超时，也容易让一个错误污染其它判断。当前分析拆成五个职责单一、可缓存和可从失败点继续的阶段。

| 顺序 | 阶段 | 输入重点 | 产出 | 不负责什么 |
| --- | --- | --- | --- | --- |
| 1 | `characters` | 全章正文、预切分片段、已有角色名册 | 本章真正需要独立配音的角色、别名、性别、年龄、置信度 | 不分配每句说话人，不写情绪或音效 |
| 2 | `voice_design` | 已确认角色、已有稳定音色设计、正文中的身份/性格线索 | 每位活跃角色的长期稳定 MiMo 音色设计 | 不为当前句重新设计声音，不写临时情绪 |
| 3 | `speakers` | 固定角色名册、完整上下文、所有片段 | 每个片段的 `speakerId`（角色、`narrator` 或 `unknown`） | 不新建角色，不判断情绪/语速 |
| 4 | `delivery` | 已固定的说话人和片段文本 | 每句的 `emotion` 与粗粒度 `pace` | 不改角色或说话人 |
| 5 | `voice_direction` | 前后相邻片段、关系、情绪与语速 | 给 MiMo 的细粒度演绎指导：节奏、停顿、气息、重音、句尾和情绪起伏 | 不改固定音色、角色、音乐或音效 |
| 6 | `script` | 前五阶段结构化结果 | `scripts/<chapter>.json` 章节脚本 | 不是一次新的 LLM 判断 |

在 LLM 前，`dialogue.py` 会先做本地文本预切分，区分普通旁白、直接对白、内心独白和“引用材料”。被标记为 `quoted_material` 的书名、公告、诗句、被提及的称谓等会保持为旁白，避免被误配给角色。

### 角色一致性如何保证

1. 选中章节按书籍顺序分析。
2. 已成功章节的完整角色名册会传给下一章。
3. Python 层而不是 LLM 自行生成持久 ID：同一书内使用稳定 `char_*` 角色 ID，并合并规范名与别名。
4. 已有角色的稳定 `voiceDesign` 会优先原样继承；手工指定的音色不会被后续单章重新分析覆盖。
5. 每个片段最终写入 `speakerId`、`voiceId`、`voiceDesign`、`emotion`、`pace`、置信度和源文本位置。

旁白是书籍级设置，当前支持 `narrator_female`、`narrator_male` 和兼容用的 `narrator_default`。旁白的固定性别和基础音色不由每段 LLM 重设；每段仅可改变演绎方式。

### 状态、缓存与失效规则

- 每个阶段的 JSON 与状态写到 `analysis/<chapter>/`；网页轮询 `state.json` 显示步骤进度。
- 缓存以“正文、语言、书籍/章节 ID、已知角色、阶段版本”为签名。只有明确从中间阶段继续时，才复用匹配的前序产物。
- 一次新的完整分析会删除该章旧的原配音、最终混音、音频资源清单和 TTS 时间线，防止旧时间轴混入新脚本。

## 8. 阶段三：人工审阅（可选）

网页分析完成后会自动进入生成，不必先审阅；审阅仍用于人工控制质量。当前校正能力包括：

- 修改角色性别、合并别名、调整角色音色分配和稳定音色描述；
- 试听可用的声音选项；
- 在书籍级切换旁白男声/女声；
- 将修改应用到受影响章节的脚本，并持久化到角色名册。

保存校正会重建相应脚本并使相关原配音、最终混音、资源清单和时间线失效。这样做的目的不是增加等待，而是避免“文本/角色已改、仍播放旧音频”的错配。

## 9. 阶段四：原章节配音（`voice`）

这一阶段产生还没有背景音乐、音效的“原章节配音” WAV。

1. 服务读取章节脚本，并应用书籍当前的旁白选择。
2. 片段会按 TTS 长度限制安全合并或拆分；合并/拆分后仍保留 `sourceSegmentIds`，后续可映射回原文时间线。
3. 为每个待生成片段附加短场景上下文（前文、当前句、后文）和第 5 个分析阶段生成的动态演绎指导。
4. 默认使用 `mimo-v2.5-tts-voiceclone`。每个角色/旁白先生成或复用一个稳定参考样本，再由后续片段严格复用该参考音色。
5. 对 MiMo 实际发送的逻辑由四部分构成：**固定音色身份约束 + 场景上下文 + 本句动态指导 + 待朗读文本**。临时的情绪、语速和场景只能改变演绎，不应改变说话者身份。
6. 所有片段 WAV 校验通过后，按源顺序拼接，片段之间默认插入 `0.5` 秒静音，写入 `audio/<chapter>.wav` 与 `segments/<chapter>/timeline.json`。

### 音色稳定机制

- `voice-profiles/` 中的参考 WAV 按“角色 ID + 稳定音色设计 + 参考模型 + 固定参考文本”签名缓存。
- 参考样本生成时刻意不带当前场景、情绪或语速；它只建立性别、年龄、音高、共鸣、气息和咬字基线。
- 并行章节共用同一本书的 profile 时，使用进程内锁和 `fcntl` 文件锁；临时 WAV 先校验再原子替换，避免并发生成导致参考音色损坏或漂移。
- 旁白请求额外要求保持当前旁白的固定性别、年龄、音高和基础音色，不模仿角色。

### 失败与缓存

- 已存在且签名匹配、可读的片段 WAV 会复用；重新生成可关闭缓存并强制生成。
- MiMo 的可重试网络、408、425、429 和服务端错误会在同一条全局单请求通道内按指数退避有限重试；默认单请求最多 3 次。
- 参考音色、章节片段、直接单段合成和重试都严格串行。实际请求启动按最多 80 RPM（相邻至少 0.75 秒）节拍发送；429 会优先遵守 `Retry-After`，并让整个队列进入共享冷却。已成功片段不会重复生成。
- 如果最终混音前发现原章节 WAV 与当前片段时间线不一致，系统会优先在安全条件下用现有片段重组原章节 WAV；无法验证时才报告时间线不匹配，要求重新生成原章节配音。

## 10. 阶段五：Whisper 转录（`transcript`）

背景音乐与音效必须落在实际读到某段文字的时刻，不能只凭字符位置猜测。因此原章节配音完成后，系统会调用本地 `mlx-whisper` 转录 WAV，生成每段 `start` / `end` / `text`。

- 默认模型：`mlx-community/whisper-large-v3-turbo`。
- 优先使用当前 Worker 环境；若未安装，会查找显式传入的 Python、`AUDIOBOOK_WHISPER_PYTHON`、本机已知的 MLX 环境和 PATH 中的 Python。
- Hugging Face 模型如已在本地缓存，会直接使用本地快照；首次没有缓存时才需要下载。
- 输出为 `analysis/<chapter>/transcript.json`，它是音频规划的前置条件。

因此 `ModuleNotFoundError: mlx_whisper` 的根因是“被调用的 Python 环境没有这个模块”，不是小说文本或 MiMo 配音本身失败。

## 11. 阶段六：背景音乐与音效规划（`audio_plan`）

该阶段由 LLM 负责写结构化计划，而不是直接生成声音。它同样拆成三个可恢复小阶段：

| 顺序 | 子阶段 | 做什么 |
| --- | --- | --- |
| 1 | `scene_structure` | 阅读全章、脚本片段、Whisper 时间戳和活跃角色，划分场景、时间跳转、回忆、环境底色与张力变化 |
| 2 | `music` | 以场景为单位规划背景音乐的 palette、变体、进入/退出、停顿与循环方式；长章会拆成受限场景批次请求，避免把整章塞进一次 LLM 请求 |
| 3 | `sfx` | 只为正文或动作明确发生的声音创建音效 cue，记录场景、资产 ID、锚点片段和必要的 `anchorText` |

规划完成后会：

- 校验场景范围、音乐/音效 ID 和模型类型；同类资产 ID 在多个章节/场景中保持唯一，避免 `duplicate audio asset`；
- 写入脚本的 `audioPlan`，并保存 `audio_plan.json`；
- 对背景音乐执行覆盖补足：连续对白不能让环境底色意外消失，但也不会机械地让同一首有节奏音乐从头到尾不变；场景 palette、变体、休止和交叉衔接由计划表达；
- 使旧最终混音与旧资源清单失效，不删除仍可复用的原章节配音。

## 12. 阶段七：本地 Stable Audio 资源生成（`stable_audio`）

规划中的每个音乐或音效资产会转换成独立的 `AudioAssetSpec`，并调用本地 Stable Audio CLI：

```text
stable-audio-3/optimized/mlx/sa3
  --prompt <LLM 规划后的短提示词>
  --dit sm-music 或 sm-sfx
  --decoder same-s
  --seconds <时长>
```

关键行为：

- 音乐使用 `sm-music`，音效使用 `sm-sfx`；每个资源时长上限为 120 秒。
- 资源以“计划内容 + Stable Audio 配置”签名缓存。签名和可读 WAV 都匹配时复用，重生成按钮才会强制覆盖。
- 资源写入 `audio-assets/<chapter>/music` 或 `sfx`，`manifest.json` 是混音器识别资源的唯一清单。
- 每个新背景音乐在进入混音前用 ffmpeg 做一次响度归一化，目标为 **-18 LUFS**、**-2 dB true peak**、**LRA 7**，用于削弱不同批次音乐的响度波动。
- 当前主流程直接在后台调用本地 CLI，不会把浏览器跳转到 `7860`，也不会等待 Gradio 浏览器回调。`7860` 只在某个资源未通过质量门后的单资产后台重生成中使用；它不是批量生产链路的浏览器任务入口。
- 音乐响度归一化后、写入 manifest 前，会对 `music` 与 `sfx` 执行尖锐声/爆鸣/削波检测。正常资源才会进入 manifest；短异常会保留原件、切除异常区间并交叉淡化后复检，无法修复的资源最多经 7860 单资产重生成两次。
- 仍不合格的 WAV 会移入 `rejected/` 并记录质量报告，不会参与混音。音效会被省略；背景音乐优先使用同场景合格变体，随后使用相邻场景的合格音乐铺底。

## 13. 阶段八：最终混音（`mix`）

混音器不会按“第 N 段文字”生硬叠加音频，而是先读取实际 TTS WAV 时长，建立真实时间线，再借助 `sourceSegmentIds` 将规划的文本片段映射到最终语音时间轴。

- **背景音乐**：按场景放置；需要覆盖时可以循环到对应时长；场景变化使用默认 `0.75` 秒交叉衔接和各轨淡入淡出。
- **音效**：通过片段索引定位；若规划给出 `anchorText`，会在片段正文中寻找其位置，以比例估算更精确的声音落点，而不是总放在该段开头。
- **对白压低音乐**：ffmpeg 对人声作 side-chain ducking，音乐在人声出现时自动下降，避免盖住旁白/对白。
- **总线保护**：最终 `amix` 后使用 limiter，避免叠加后削波。

当前默认混音增益如下：

| 声道 | 系数 | 说明 |
| --- | ---: | --- |
| 原章节人声 | `1.412538` | 约 +3 dB |
| 背景音乐 | `0.40` | 相比此前 `0.32` 基线约 +1.94 dB；音乐已先做响度归一化 |
| 音效 | `0.35` | 由场景/音效轨淡入淡出后叠加 |

最终结果保存为 `audio/<chapter>_mixed.wav`。原章节配音与最终混音会同时保留，便于分别试听、下载和定位问题。

## 14. 音频质量检测与安全降级

项目已有 `audio_quality.py`，可以用 ffmpeg 的短窗峰值、6 kHz 以上高频能量、局部/全局突增、频谱质心、平坦度、rolloff 和削波统计，标记疑似尖锐声、爆鸣或削波。当前峰值阈值为 **-10 dBFS**。

它已接入 Stable Audio 的 `music` / `sfx` 资产主链路：音乐归一化后、写入 `manifest.json` 前检测。质量报告位于 `audio-assets/<chapter>/quality/<kind>/`；异常候选会保留在 `rejected/`，不会通过旧文件名回退重新混入最终混音。

可修复的短异常会先切除并以交叉淡化拼接，再用同一检测器复检。小于 3 秒的音效不会被切除，直接只重生成该资产。修复失败、检测失败或两次后台重生成仍异常时，章节继续混音：拒绝的音效省略，拒绝的音乐使用同场景或邻近场景的合格替代。整个过程不需要人工试听或浏览器跳转。

检测器仍可单独用于定位已有 WAV：

```bash
cd "audio book-generator"
workers/python/.venv/bin/python -m audiobook_worker.audio_quality /绝对路径/文件.wav
```

输出会给出风险状态、疑似时间点、异常时间段和原因。生产链路会将同类结果记录到质量报告中，供后续检查和恢复原件。

## 15. 批量生成、并发与恢复

### 章节内顺序

一章进入批量任务后的固定顺序为：

```text
voice_synthesize → voice_assemble → transcript → audio_plan → stable_audio → mix → complete
```

前两个内部检查点共同显示为用户可见的 `voice`：前者只生成片段和时间线，后者按片段组装原章节 WAV。每个检查点完成后才会使下一个检查点 `ready`；任一阶段失败，该章节记录失败的阶段和错误，其他章节不会被中断。

### 章节间并发

批量任务保存在 SQLite 的 `generation_batches` 与 `generation_batch_chapters` 中，而不是只存在浏览器内存。每章行还持久化 `next_stage` 与 `stage_state`；调度器以“一个 `ready` 阶段 → `running`”的数据库原子转换认领工作，同一检查点不会被两个调度器重复执行。

MiMo 使用全服务、跨 worker 子进程的单请求通道。参考音色、普通片段、直接合成和重试都会先获取同一个文件锁；请求启动全局限制为 80 RPM（至少相隔 0.75 秒），并且不允许突发。HTTP 429 会解析 `Retry-After`；若服务未给出该头，则使用带随机抖动的有界指数退避，冷却会阻止后续所有 MiMo 请求启动。

这使吞吐的关键变化成为可能：第 1 章完成 `voice_synthesize` 后，worker 立即释放，下一章可进入 MiMo；第 1 章的组装、转录、规划、Stable Audio 和混音则在其他 worker 上继续。MiMo 仍待处理时，调度器为它保留一个总 worker 位置，因此最多只会运行 4 个非 MiMo 阶段。

当前安全上限如下：

| 资源 | 默认/上限 | 原因 |
| --- | ---: | --- |
| 同时运行的批量阶段 worker | 5 / 5 | 为 4 个本地音频任务和 1 个串行 MiMo 任务预留容量 |
| MiMo 全部请求 / 单进程片段请求 | `1 / 1` | 全服务强制串行，不能被环境变量提高 |
| MiMo 请求启动速率 | `80 RPM / 80 RPM` | 小于官方 100 RPM；全模型共享、无突发 |
| LLM Worker | 2 / 2 | 避免模型网关请求过大/过多 |
| 本地音频（Whisper 与 Stable Audio 合计） | 4 / 4 | 经过压测验证的稳定档位；两类任务合计不超过 4，不能理解为 `4 + 4` |
| VoxCPM2 章节客户端 / 常驻模型服务 | 4 / 4 | 最多四章客户端共用一个按需启动的本地模型；服务只对跨章节、可独立生成且长度相近的片段做真实张量 batch，批量和直接请求共用客户端资源位 |
| 原章节组装、混音与 MP3 转换 | 2 / 2 | 限制 ffmpeg 并发 |

可用的环境变量为 `AUDIOBOOK_BATCH_WORKER_CONCURRENCY`、`AUDIOBOOK_MIMO_TOTAL_CONCURRENCY`、`AUDIOBOOK_MIMO_CONCURRENCY`、`AUDIOBOOK_MIMO_RPM`、`AUDIOBOOK_LLM_WORKER_CONCURRENCY`、`AUDIOBOOK_LOCAL_AUDIO_WORKER_CONCURRENCY`、`AUDIOBOOK_VOXCPM_WORKER_CONCURRENCY`、`AUDIOBOOK_VOXCPM_BATCH_SIZE`、`AUDIOBOOK_VOXCPM_IDLE_SECONDS`、`AUDIOBOOK_MIX_WORKER_CONCURRENCY`。无效、零或超过硬上限的值都会被安全钳制；前两个历史 MiMo 并发变量只为兼容保留，实际始终为 `1`，而 `AUDIOBOOK_MIMO_RPM` 只能将预算调低到 `1..80`。旧的 `AUDIOBOOK_MLX_WORKER_CONCURRENCY` 仍被读取为兼容上限；若它显式存在，最终本地音频并发取新旧两个设置中更小的值。`AUDIOBOOK_VOXCPM_WORKER_CONCURRENCY` 默认/上限为 `4`，只能调低，批量和直接 VoxCPM2 请求合计不超过该值；`AUDIOBOOK_VOXCPM_BATCH_SIZE` 只接受 `auto`、`1`、`2`、`4`，其中 `auto` 在没有匹配当前适配器版本的合格基准选择文件时强制为 `1`；`AUDIOBOOK_VOXCPM_IDLE_SECONDS` 为 `0..3600`，默认 `300`，控制最后一项本地任务完成后多久释放模型。

### 状态与停止

- 网页每约 1.2 秒查询批量状态，并以每章的 `nextStage` / `stageState` 为准显示“等待 MiMo 串行配音”“MiMo 配音中”或后续阶段；429 共享冷却时会显示剩余等待时间。终态结果会立即写入页面状态，无需重新选择章节刷新。
- 停止任务会阻止新检查点被认领；已进入子进程的检查点会运行到当前边界，再安全标为 `cancelled`，避免截断 WAV 或 manifest。
- 服务重启时，只会把 `stage_state=running` 的当前检查点恢复为 `ready`，保留已经完成阶段的音频、转录、计划、资源和耗时；批次只有不存在 `queued` 和 `running` 章节时才会结束。

| `GET` | `/api/books/<bookId>/chapters/<chapterId>/text` | 章节正文文本 |
| `POST` | `/api/books/import?filename=…` | 上传并导入 EPUB/PDF/TXT，支持 multipart 或原始请求体 |
| `POST` | `/api/books/<bookId>/final-audio.zip` | 将当前书内选定的已完成最终混音打包为 MP3 或 WAV ZIP |
| `DELETE` | `/api/books/<bookId>` | 删除书及其受管理数据 |
| `GET` | `/api/audio/<bookId>/<chapterId>` | 原章节配音 WAV |

### 浏览器调用桥

前端通过 `POST /api/invoke` 发送：

```json
{
  "command": "batch_generation_start",
  "args": {
    "bookId": "book_xxx",
    "chapterIds": ["chapter_001", "chapter_002"],
    "force": false,
    "cacheSegments": true
  }
}
```

主要命令按类别如下：

| 类别 | 命令 |
| --- | --- |
| Worker 调用 | `run_worker`（再传入 `extract_book`、`analyze_chapter`、`transcribe_chapter_audio`、`plan_chapter_audio`、`synthesize_chapter_audio`、`assemble_chapter_audio`、`generate_audio_assets`、`mix_chapter_audio`、`convert_to_mp3` 等） |
| 批量队列 | `batch_generation_start`、`batch_generation_status`、`batch_generation_active`、`batch_generation_cancel` |
| 旧单章 Stable Audio 兼容接口 | `stable_audio_start`、`stable_audio_status`、`stable_audio_cancel`；它同样走后台本地 CLI，不再是浏览器 Gradio handoff |
| 书库/角色 | `db_list_books`、`db_get_book`、`db_create_book`、`db_delete_book`、`db_get_chapters`、`db_upsert_chapter`、`db_get_characters`、`db_upsert_character`、`db_set_narrator_voice` |
| 受控文件操作 | `file_exists`、`copy_file`、`book_work_dir`、`_read_file`、`_write_file` |

Worker 的通用返回结构为 `status`、`warnings`、`artifacts`，失败时附带 `error.code`、`error.message` 和可能的 `error.details`。网页将这些错误显示在具体章节和具体阶段上。

### 当前书籍最终配音批量下载

`POST /api/books/<bookId>/final-audio.zip` 接受 JSON：

```json
{
  "chapterIds": ["chapter_001", "chapter_002"],
  "format": "mp3",
  "bitrateKbps": 192
}
```

`format` 必须为 `mp3` 或 `wav`。MP3 必须提供 `128`、`192`、`256`、`320` 之一，服务端用固定 CBR 转码；WAV 不提供 `bitrateKbps`，直接打包原始最终混音。服务端再次校验章节属于该书且最终混音可读，缺失的文件会跳过；若全部不可读则返回 JSON 错误。成功响应为 ZIP，带有 `X-Audiobook-Chapter-Count` 和 `X-Audiobook-Skipped-Chapter-Count` 响应头。

批量队列响应中的每个 `chapters[]` 条目除旧有的 `status`、`currentStage` 和耗时字段外，还包含 `nextStage`（下一条精确 worker 命令）与 `stageState`（`ready`、`running`、`complete`）。批次顶层可包含 `mimoCooldownSeconds`，它只表示近期 429 的共享冷却剩余秒数。前端必须以章节条目为准；顶层 `currentChapterId` / `currentStage` 仅是兼容摘要，不能用于判断并行进度。

### 外部自动化接口的完整行为

`POST /api/external/audiobook/chapters.mp3.zip` 接受 EPUB/PDF/TXT 上传，可用查询参数 `narratorVoiceId=narrator_female|narrator_male|narrator_default` 指定旁白。服务端会：

```text
上传 → 提取 → 按书序分析且传递角色名册 → 自动接受分析结果
→ 提交同一套批量生成队列 → 所有最终混音转 MP3 → 返回 ZIP
```

这是同步长请求，默认最长等待 24 小时（`AUDIOBOOK_EXTERNAL_AUTOMATION_TIMEOUT_SECONDS`）。成功响应是 ZIP，并附带书 ID 与章节数响应头；失败响应是 JSON，包含失败章节及阶段。外部自动化不会等待人工审阅。

## 17. 启动、配置与运行边界

### 启动方式

```bash
# 生产式局域网网页：先构建前端，再由 8000 提供页面和 API
npm run web

# 开发：Python API 8000 + Vite 5173
npm run web:dev
```

`npm run web:dev` 会让 Vite 将 API 请求代理到 `8000`。`7860` 若单独启动，通常是 Stable Audio Gradio 界面；当前正式生成并不依赖浏览器访问该端口。

### 关键配置

| 配置 | 用途 |
| --- | --- |
| `AUDIOBOOK_DATA_DIR` | 主机数据目录 |
| `AUDIOBOOK_WEB_HOST` / `AUDIOBOOK_WEB_PORT` | 网页服务监听地址和端口 |
| `AUDIOBOOK_LLM_MODEL` | 项目根 `.env` 中的 OpenAI 兼容模型 ID；可在网页“模型配置”页直接修改 |
| `AUDIOBOOK_LLM_BASE_URL` | 项目根 `.env` 中的 OpenAI 兼容服务 URL；项目值优先于历史 `models.json` 提供方 URL |

| `AUDIOBOOK_*_CONCURRENCY` | 批量任务的安全并发调节，见上一节 |

### 当前不属于已完成主功能的内容

- 没有多用户登录、权限控制或书库隔离。
- 没有分布式队列/多台机器 worker；所有生成都在一台主机及其配置的外部 LLM/MiMo 上完成。
- 没有“把小说翻译成另一种语言再配音”的翻译功能；当前的语言检测、中文/英文提示词和 TTS 处理不等于翻译。
- 不检测 MiMo 人声、原章节配音或最终混音的音色一致性、情绪和文本正确性；当前质量门只保护 Stable Audio 背景音乐和音效。
- 浏览器不再自动跳转 7860，也不再使用“Gradio handoff/callback”模式。
